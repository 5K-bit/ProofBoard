Teams say things like "the restore works", "coverage is above 90%" and "no runtime dependencies". ProofBoard turns each of those into a **claim** in a small file, links it to the **evidence files** that back it (a test log, a coverage report, a drill transcript), and **seals** their SHA-256. From then on `proofboard check` tells you, claim by claim, whether the evidence is still **proven**, or has gone **missing**, **drifted** (changed after sealing), **failed** a content rule, or gone **stale**.

**Pre-release.** An engineering tool for demonstration and controlled trials, not for unattended production use.

### What it does

- A claims file (`proofboard.toml`) that links each claim to evidence files, with strict validation (unknown keys, bad paths and duplicate ids are errors).
- Content rules per evidence file: `contains`, `not_contains`, `matches`, `coverage_min` (coverage.xml, coverage.json or a pytest-cov `TOTAL` line) and `junit_clean`.
- A lock file recording the SHA-256 of every evidence file, with its own digest so hand edits are caught.
- Claim statuses: proven, stale, unsealed, drifted, missing, failed, no evidence.
- `proofboard init`, `seal` (refuses silent changes; `--accept-changes`, `--refresh`), `check` (exit 2 unless every claim is proven; text or JSON) and `board` (Markdown, HTML or JSON; `--strict`).
- A demo project and an acceptance script whose transcript is recorded in `docs/evidence/`.
- Case studies. A `[casestudy]` table and `[[story]]` tables describe a write-up in six fixed sections; every sentence must cite evidence and becomes a claim that `seal` and `check` already cover.
- `proofboard casestudy` renders Markdown or one self-contained HTML page (screenshots embedded, text escaped) with each sentence's evidence status; `--strict` exits 2 unless all are proven.
- `proofboard scaffold` drafts a case study from ADRs, test logs, screenshots and README limitations, leaving `TODO` where a human sentence is needed.
- This repository's own case study.

### Known limitations

- **Unchanged is not true.** A seal proves a file is what it was when sealed, not that it was honest. Write rules that would fail if the claim were false.
- **The lock is tamper-evident, not signed.** Anyone who can rewrite both the lock and the evidence can make a board green. Commit the lock and review its diffs.
- **It does not run your tests.** You produce the evidence; ProofBoard checks it. Nothing from a claims file is ever executed.
- **Rules are simple.** Text, regular expression, a coverage figure, JUnit totals. A rule like `contains = "passed"` is satisfied by the word anywhere in the file.
- **Staleness uses the sealing machine's clock.**
- **Tested on made-up projects.** The demo and the fuzzing are hand-built. Real reports from other tools may expose gaps in the coverage and JUnit readers; send a sanitised example if one fails.
- **Not yet verified on Windows by hand.** CI runs the tests on Windows; nothing has been checked against a real Windows workflow.
- **A case study is only as good as its sentences.** ProofBoard checks that each cited file is unchanged and meets its rule; it cannot tell that a sentence says what the file shows. `scaffold` writes the structure, not the story.
- **Links in a case study are not checked.** Commit and issue URLs are shown as given and labelled so; nothing is fetched.
- **Only this repository's own case study has been built so far.** It has not yet been used for another project.

Checksums are in `SHA256SUMS`. See the [changelog](https://github.com/5K-bit/ProofBoard/blob/v0.1.0/CHANGELOG.md) for details.
