ProofBoard: claims tied to evidence you can re-check

proofboard 0.1.0 · by Louis Boddie · repository

A small command-line tool that links each claim about a project to the evidence files behind it, seals their SHA-256, and reports when that evidence changes, goes missing, fails a rule or goes stale.

As of 2026-10-31T21:00:00Z, all 11 statements are backed by sealed, unchanged evidence.

The problem

  1. The evidence behind a claim can be edited, deleted or left to age while the claim keeps being repeated, and nothing in a normal repository notices. The recorded demo walks one made-up project through exactly those three failures. PROVEN

What the evidence showed

  1. In that recording all four claims read proven after sealing; after the restore drill is edited one reads drifted and a repeat seal is refused; after enough time all four read stale. PROVEN
    • ok docs/evidence/acceptance-transcript.txt · sha256 07ae788e57ae

Decisions

  1. Evidence is sealed by SHA-256 rather than by file time, because modification times change on every checkout and can be set by anyone. PROVEN
    • ok docs/adr/0001-seal-by-hash-not-by-timestamp.md · sha256 b904e054f54b
  2. Sealing refuses to overwrite a changed hash unless told the change is expected, so the seal command cannot be used to turn a red board green by accident. PROVEN
    • ok docs/adr/0002-seal-refuses-silent-changes.md · sha256 65f3f2239da2
  3. Rules are data, not code: a claims file cannot run a command, so editing it in a pull request is not the same as running code in CI. PROVEN
    • ok docs/adr/0003-rules-are-data-not-code.md · sha256 5264b129bc47

Implementation

  1. A strict claims-file parser, a hash ledger with its own digest, a pure planner for sealing, and an evaluator that gives each claim the worst status among its evidence, with text, Markdown, HTML and JSON reports. PROVEN
    • ok docs/architecture.md · sha256 85a520dbefcc

Remaining limits

  1. A seal proves a file is what it was when sealed, not that it was honest; a sealed false log reads as proven. PROVEN
    • ok README.md · sha256 7196aa679a16
  2. The lock is tamper-evident, not signed: anyone who can rewrite both the lock and the evidence can make a board green. PROVEN
    • ok README.md · sha256 7196aa679a16
  3. It has only been tried on made-up projects, and not yet by hand on Windows. PROVEN
    • ok README.md · sha256 7196aa679a16
